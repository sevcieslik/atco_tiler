1. Input-first validation and processing

v1.08-dev does not display a catalogue of all W-drive entities. An operator first supplies a local input folder containing aoi, orthos and point_cloud as needed by the selected products. The central registry is only a read-only geometry/revision reference.

StageBehaviour and guardrail

The local AOI must match the full current circuit polygon exactly, or cover at least 99% of a registered area AOI. Selected imagery and/or LiDAR input file extents must separately cover at least 99% of the candidate geometry. A circuit also requires its approved published segment index. These are source footprint checks; they do not verify the actual count of valid image pixels, point density or gaps inside files. The processing pipeline and QA remain responsible for those checks.

Changing input sources or selected products invalidates the prior eligibility result. Run Validate Input again. If no entities qualify, check the Activity Log for excluded entities and missing coverage rather than selecting unrelated polygons from W:.

1. Authoritative sources and geometry

Retiler never publishes registry changes. It matches local input AOI and source coverage against the current entries in the existing central entities/revisions tables. Only qualifying entities are shown after Validate Input. Circuit processing loads the approved segment index; standalone area processing uses the current registered polygon without segments.

3. TIFF generation

Purpose: 4-band RGBI outputs. Circuits generate approved segment tiles; registered area AOIs generate one whole-area TIFF with no segment index.

  • Source TIFFs are validated for CRS, pixel size, common pixel lattice and 4-band RGBI content.
  • For circuits, Retiler creates internal Ortho Processing Footprints aligned to the source pixel grid. These are processing footprints, not the client Tile Index. Large standalone areas use windowed BigTIFF export to bound RAM consumption, with a free-disk-space preflight.
  • Source imagery is mosaicked/cropped to circuit processing footprints or to a standalone area polygon and masked outside the approved entity AOI.
  • Final TIFF remains four bands: Red, Green, Blue, NIR. Band 4 is not Alpha.
  • The all-four-band tuples 254,254,254,254 and 255,255,255,255 are treated as background during source mosaicking; valid overlapping image pixels can fill such areas.
  • ArcGIS Pro compatibility rollback: the delivered 4-band TIFF carries explicit NoData=255 and background pixels are 255 across all bands. Valid individual source values of 255 are adjusted to 254 to avoid accidental NoData masking by band-level renderers. Band 4 remains NIR, never Alpha.
  • Final GeoTIFF is tiled, LZW compressed, 512 × 512 internal blocks.
QA: inspect at least one edge/overlap location in ArcGIS Pro. Confirm outside-AOI background is automatically transparent/NoData in ArcGIS Pro without manually changing symbology, band 4 remains NIR, and no white/black edge artefacts are visible.
Source imagery QA: The Retiler merges overlapping source TIFFs independently for each approved tile. It does not first create a single full-corridor mosaic. If the input TIFFs were already cropped and contain missing image coverage or white fringes, this may limit results. Prefer full-coverage, uncropped source imagery where available; compare tile 0008/0009 against a full source mosaic before interpreting edge artefacts as a clipping defect.

4. ECW generation

Purpose: RGB-only visual ECW for PLS-CADD and GIS display. This is not the 4-band RGBI TIFF deliverable.

  • Generated from the final TIFF, using only its Red, Green and Blue bands. NIR is excluded.
  • Global Mapper source intermediates are written to QA\Imagery\gm_rgb_input with a new _GM_RGB3_WHITE.tif suffix. Older RGBA intermediates must not be reused.
  • Each intermediate contains exactly 3 bands (RGB), with no Alpha and no scalar NoData.
  • Pixels outside the delivered TIFF NoData mask are explicitly set to white (255,255,255). In-range valid RGB values are preserved.
  • Global Mapper receives the 3-band input without contrast enhancement and exports ECW v3, target compression 10:1, with BG_TRANSPARENT=NO.
  • Compatibility decision: the 3-band ECW does not encode transparency. A white outside-footprint background is expected. Compression may create faint edge fringes; no magenta RGB fill or fourth Alpha band should be present.
  • Following any ECW export-configuration change, select Process and confirm overwrite of existing ECWs. Process Missing does not replace already-present previous-version ECWs.
Release QA gate: build a fresh test ECW (e.g. tile 0008), verify 3-band interpretation and white/no-magenta background in Global Mapper, MicroStation Raster Manager, TerraScan and PLS-CADD. Verify alignment and investigate edge halos. Do not mark compatible before PLS acceptance. TIFF keeps its internal mask and is not altered by this change.

5. LAZ generation

Purpose: exact polygon crop of the classified source point cloud, by segment for circuits or by one registered polygon for areas.

  • PDAL inventories source LAS/LAZ and validates the horizontal CRS against the AOI.
  • Compound CRS / vertical datum from source point clouds is preserved where consistently present.
  • All intersecting source clouds are merged and cropped to the approved segment polygon (circuit) or approved whole-area polygon (area).
  • Only Classification 7 (Low Noise) is removed.
  • Other classifications and point attributes are preserved.
  • Retiler does not automatically change Synthetic flags.
Return Number 0 is a QA condition, not an automatic edit rule. The current QA reports Return 0 by Synthetic flag and classification so unusual cases such as Class 93 can be reviewed rather than silently modified.

6. zLAS generation

  • A conservative temporary uncompressed LAS is created from each final LAZ.
  • Standalone Esri EzLAS.exe converts the temporary LAS to zLAS.
  • Each zLAS is verified using EzLAS verification mode before being accepted.
  • EzLAS logs, work folders and command details are kept under QA\LiDAR\EzLAS.
  • The delivery zLAS folder is cleaned so it contains only .zlas products.
  • EzLAS processes are launched hidden. Operator-facing command windows should not appear during normal processing.
QA: load a sample zLAS in ArcGIS Pro and compare with its LAZ for extent, point count, classifications and general appearance.

7. Tile Index

Circuits only: Retiler creates an intermediate shapefile named using the circuit, year and version (for example 9L137_2026_Tiles_v1.shp) under Tile_Index. It is not the final project GDB. During final delivery assembly this SHP is imported as the TILES feature class together with the other GDB products.

8. TX trajectory attribution

The central trajectory source is built from the current/highest available processed trajectory version for each flight. The index stores flight date, flightline code and adjusted GPS-time range.

For each TX final LAZ, Retiler reads the tile GPS-time range and finds overlapping SBET/trajectory records. Matching dates populate fldate; matching codes populate Flightline. Multiple values are retained as comma-separated values.

Blank TX flight attribution means no reliable GPS-time match was found. Do not invent a value; review the trajectory index and LAZ GPS-time metadata.
